# HowlNotes Architecture

HowlNotes is a complete, minimal notes web application designed as an external consumer and dogfooding testbed for HowlFrame (`howlcipher/howlframe`).

---

## 1. System Architecture

HowlNotes is expressed directly in HowlFrame DSLs and compiled by the HowlFrame toolchain into executable targets:

```text
+-------------------------------------------------------------------------+
|                              Browser Client                             |
|  (static/index.html + static/app.css + static/app.js generated by HF)   |
+-------------------------------------------------------------------------+
                                     |
                                     | HTTP Requests (JSON over REST & RPC)
                                     v
+-------------------------------------------------------------------------+
|                     HowlFrame Bytecode Runtime (VM)                     |
|  - Executing build/backend.hfbc (compiled from app/backend.howl)        |
|  - Enforcing Capability Boundary: network, database, filesystem        |
|  - Static Asset Serving & REST/RPC Notes API Router                     |
+-------------------------------------------------------------------------+
                                     |
                                     | Structured Record Operations
                                     v
+-------------------------------------------------------------------------+
|                    HowlFrame Native Persistent Store                    |
|  - URI: file://data/notes.json                                          |
|  - Atomically synchronized JSON record storage on local disk            |
+-------------------------------------------------------------------------+
```

---

## 2. Compilation and Execution Pipeline

1. **Frontend Compilation:**
   - **Source:** `app/frontend.howl` using the `(web_app ...)` construct.
   - **Compiler Target:** HowlFrame JavaScript backend.
   - **Output:** `static/app.js` (vanilla browser JavaScript with async fetch, DOM query/mutation, and event listeners).

2. **Backend Compilation:**
   - **Source:** `app/backend.howl` using the `(http_server ...)` construct.
   - **Compiler Target:** HowlFrame Standalone Bytecode (`-compile-bc`).
   - **Output:** `build/backend.hfbc` (binary bytecode format HFBC v1).

3. **Backend Execution:**
   - **Runtime:** `howlframe -run-bc -allow-caps network,database,filesystem build/backend.hfbc`.
   - **Authority Model:** "Intent is not authority". The VM executes with finite instruction limits and verifies capability tokens at each privileged opcode (`HTTP_SERVER_START`, `STORE_OPEN`, `STORE_PUT`, `STORE_GET`, `STORE_DELETE`, `READ_FILE`).

---

## 3. Data Model

Notes are persisted as structured records:

```json
{
  "id": "1",
  "content": "Buy groceries and finish dogfooding",
  "created_at": "1787190354",
  "updated_at": "1787190354"
}
```

Store state layout in `file://data/notes.json`:
- `_seq`: `{"val": <integer>}` — auto-incrementing ID sequence.
- `_all_ids`: `{"ids": ["1", "2", ...]}` — active note ID registry for $O(N)$ scans.
- `"<id>"`: Structured note object.

## 4. API Endpoints

All endpoints support CORS (`Access-Control-Allow-Origin: *`) and return JSON responses:

| Method | Path | Description | Input Payload | Response |
|---|---|---|---|---|
| `GET` | `/api/health` | Health and storage check | None | `200 {"status":"ok","app":"howlnotes","persistence":"..."}` |
| `GET` | `/api/notes` | List all saved notes | None | `200 {"notes": [...]}` |
| `POST` | `/api/notes` | Create a new note | `{"content": "..."}` | `201 {"id":"...","content":"...","created_at":"...","updated_at":"..."}` |
| `POST` | `/api/notes/get` | Fetch note by ID | `{"id": "..."}` | `200 {...}` or `404 {"error":"not_found"}` |
| `PUT` | `/api/notes` | Update an existing note | `{"id": "...","content": "..."}` | `200 {...}` or `404 {"error":"not_found"}` |
| `DELETE` | `/api/notes` | Delete a note | `{"id": "..."}` | `200 {"status":"ok","deleted":"..."}` or `404` |
| `GET` | `/` | Serve index.html | None | `200 text/html` |
| `GET` | `/app.css` | Serve app.css | None | `200 text/css` |
| `GET` | `/app.js` | Serve app.js | None | `200 application/javascript` |

## 5. Security and Input Validation

Input from HTTP clients is treated as untrusted and validated prior to state mutation:
- **Malformed JSON:** Handled via `(try_let (body (parse_json ...)) (catch ...))` returning `400 {"error":"invalid_json"}`.
- **Empty Content:** Checks `(= content "")` returning `400 {"error":"content_required"}`.
- **Missing IDs:** Returns `400 {"error":"id_required"}`.
- **Oversized Content:** Checks string length <= 10,000 chars, returning `400 {"error":"content_too_long"}`.
- **Nonexistent Notes:** Lookups yielding `nil` return `404 {"error":"not_found"}`.

---

## 6. Capability & Authority Boundary

HowlNotes enforces deterministic capability gating:

```text
[Runner Grant]
  ├── network     --> Authorizes HTTP server startup, route handling, and responses
  ├── database    --> Authorizes store_open, store_get, store_put, store_delete
  └── filesystem  --> Authorizes file:// store disk sync and read_file for static assets
```

If any capability is omitted, the VM immediately panics with a structured `CAPABILITY_DENIED` error and terminates the operation without granting unearned authority.
